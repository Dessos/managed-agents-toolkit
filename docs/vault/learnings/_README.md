# `learnings/` — Empirical findings

> One file per generalizable lesson. Cites a concrete event (test failure,
> log line, surprise) that made the world legible.

## Learning vs ADR — what's the difference?

| Question | Note type |
|---|---|
| "We chose X over Y. Here's why." | **decision** |
| "X is brittle because Y. Here's how we know." | **learning** |
| "We measured X vs Y. Here are the numbers." | **evaluation** |

A learning is the *raw material* an ADR or evaluation might later cite. Don't conflate the two — learnings can be tentative ("confidence: medium" is fine); ADRs are committed positions.

## When to write a learning

- A test failed in a way that revealed a missing invariant.
- A change worked / failed in a way the prior model didn't predict.
- A debugging session turned up a non-obvious gotcha worth naming.
- Operator made a remark that crystallizes a tacit principle.

## How to write one

```bash
cma vault new-learning <kebab-slug>
```

Fill: **What happened, What was learned, Why it surprised us, Mitigation**. The other sections are optional but help future-you not re-discover.

## Filename convention

Same as ADRs: `YYYY-MM-DD-<kebab-slug>.md`. Date = when the learning crystallized (often the test-failure date or the commit that prompted reflection).

## When to promote a learning → ADR

When you cite the same learning in three separate conversations or decisions, that's the signal to formalize it as an ADR. Cross-link the ADR's `related:` field to the source learning.
